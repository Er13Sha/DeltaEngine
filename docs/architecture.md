# Архитектура ИИ на логических дельтах для развертки материи

> **Примечание (27.10.2026).** Документ описывает прототип LogicalDeltaCorrect; код прототипа в проект DeltaEngine не перенесён (решение заказчика: строим с нуля). Принципы и требования из него учтены в [delta-engine-spec.md](delta-engine-spec.md); упоминания модулей (`delta_core.py`, `proof_engine.py` и других) относятся к старому коду.

Этот документ фиксирует уточненную инженерную постановку проекта. Материалы Катющика и пользовательские схемы используются как требование к форме модели: строгие определения, бинарные развилки `A / not A`, последовательная развертка результата и запрет расплывчатых промежуточных сущностей.

## Достижимая цель

Проект не должен обещать полную физическую развертку Вселенной без допущений. Рабочая цель: замкнутый вычислимый мир с версионированными правилами, ограниченным виртуальным объемом, точными счетчиками, строгими дельтами и проверкой инвариантов.

Корректность в прототипе означает:

- внутри фиксированного домена каждая активная дельта тотальна;
- ветви дельты взаимоисключающие;
- решатель дельты завершается за конечное время;
- следующий уровень вычисляется из канонического результата предыдущего;
- состояние хранится как текущий результат, хэш, журнал правил и редкие контрольные снимки.

## Два сцепленных контура

Онтологический контур задает термины, определения, признаки различения и допустимые бинарные ветвления. Это trusted-core: дерево материи, формат дельты, условия `total/exclusive/termination`, инварианты и журнал решений.

Эмпирический контур привязывает ветвления к справочникам, формулам и наблюдаемым свойствам. В прототипе он ограничен локальными таблицами элементов, соединений и функциональных классов. В следующей версии этот контур должен стать версионированным адаптером к внешним источникам.

## Rule-pack

Физические предпосылки нельзя смешивать в одном неразличимом основании. Поэтому правила разделяются на пакеты:

- `reference_science` - опорный режим для воспроизводимого прототипа: элемент задается атомным номером, химия строится по явным стехиометрическим рецептам.
- `katyushchik_hypothesis` - исследовательский режим: альтернативные положения Катющика оформляются как отдельный пакет гипотез, а не как безальтернативный trusted-core.

UI показывает активный rule-pack, а канонический хэш состояния включает его идентификатор.

## Слой пользовательского запроса

Запрос пользователя не входит в trusted-core как свободный естественный язык. Он проходит через отдельный детерминированный слой:

1. нормализация текста;
2. поиск понятия в локальном словаре алиасов;
3. отказ `UNKNOWN`, если понятие не найдено;
4. отказ `UNKNOWN`, если найдено несколько равносильных понятий;
5. расчет емкости целевого понятия по текущему каноническому состоянию.

Такой слой сохраняет корректность: программа не обязана “понимать все”, но обязана не выдавать догадку как доказанный результат.

Подтвержденные химические понятия хранятся отдельным снимком `data/confirmed-concepts.json`. Текущий снимок содержит все 118 элементов из PubChem Periodic Table и расширенный seed соединений из `data/compound-seed.json`. В нем разделены:

- `verified` - поля из PubChem PUG-REST: atomic number, symbol, English name, atomic mass, standard state, formula, CID, IUPAC name, SMILES/InChIKey;
- локальные русские алиасы для пользовательского ввода;
- `model` - инженерные поля прототипа: phase/family и расчетные нейтроны через округленную atomic mass.

Это разделение важно: словарь можно расширять подтвержденными данными, не выдавая модельные допущения за проверенные физические факты.

Масштабирование базы идет через ingestion, а не через ручное редактирование UI-кода: новый список соединений добавляется в seed-файл или в будущий CID/name batch-импорт, после чего `scripts/build_confirmed_concepts.py` пересобирает локальный снимок с provenance.

## Вычисленный контур соединений

Поверх подтвержденного словаря добавлен отдельный файл `data/computed-compound-space.json`. Он не подменяет эмпирическую базу, а расширяет ее расчетными кандидатами для rule-pack `katyushchik_hypothesis`.

Каждый кандидат хранит:

- `formula` и точный целочисленный состав `atoms`;
- `status = possible | impossible`;
- `reasons[]` для всех отрицательных дельт;
- `decision_trace[]` с последовательностью бинарных решений;
- `particle_requirement` и `capacity` по конечному stock из конфига;
- `source.source_id = katyushchik_hypothesis.compound_space`.

Текущий решатель использует конечный домен из `data/compound-space-config.json`: ограниченный список элементов, максимальное число атомов, максимальное число разных элементов и флаг включения подтвержденных соединений. Это сделано намеренно: полный перебор всех 118 элементов даже при малых формулах быстро превращается в миллионы кандидатов и должен запускаться отдельными пакетами.

Дельты контура:

1. `compound.known_elements` - все символы формулы есть в подтвержденном каталоге элементов.
2. `compound.min_atoms` - формула содержит не меньше заданного числа атомов.
3. `compound.homonuclear_allowed` - одноэлементная многоатомная формула не проходит при включенном запрете одноименного гомоядерного отталкивания, если механизм не подтвержден.
4. `compound.repulsion_class_diversity` - для сгенерированных, не подтвержденных формул требуется минимум разных классов отталкивания.
5. `compound.noble_gas_allowed` - формулы с инертным газом требуют подтверждения.
6. `compound.resource_available` - текущий stock покрывает точную потребность `p/n/e`.

Все эти дельты тотальны на конечной записи `CompoundCandidate`, взаимоисключающи как boolean-ветви и завершаются за конечное время, потому что работают по конечной строке формулы, конечному справочнику элементов и конечным целым счетчикам.

## Формат DeltaRule

```text
DeltaRule:
  delta_id
  subject_type
  discriminator
  left_branch
  right_branch
  exhaustive = true
  exclusive = true
  invariants[]
  evidence_source[]
  state_transform()
```

`state_transform()` в классификационной дельте не меняет материальный объект, а добавляет в журнал один выбранный переход. В генеративной дельте следующего уровня `state_transform()` может создавать новый канонический агрегат, например `ParticleStock -> ElementCapacity`.

## Вычислительный конвейер

Первый рабочий прототип стартует не с кваркового уровня, а с эффективного набора:

1. `proton / neutron / electron` в ограниченном виртуальном объеме.
2. Элементы ограниченного диапазона через целочисленные счетчики.
3. Простые соединения через стехиометрические рецепты.
4. Био- и техно-классы через функциональные шаблоны.
5. Классификация каждого объекта по бинарному дереву материи.

Такой прототип уже демонстрирует главное свойство: каждый уровень берет результат предыдущего и не требует хранить все возможные варианты в памяти.

## Точные типы

В trusted-core используются целые числа для счетчиков частиц и зарядов. Рациональные числа нужны для будущей стехиометрии, если появятся дробные коэффициенты. Символы масштаба вида `L, R, T, n` не должны попадать в `float/double`; их нужно реализовывать отдельной символьной алгеброй порядка величин.

Новый модуль `exact_algebra.py` фиксирует это как `SpaceFormatting`: `R`, `n`, `L = R*n`, `T = R/n`. При наличии `sympy` используются символьные выражения SymPy; без него сохраняются строковые символические токены, чтобы trusted-core не переходил на приближенную арифметику.

Модуль `exact_polynomial.py` реализует программный фрагмент `Q[n,n^-1]` через `Fraction`. Он намеренно отвергает `float`, чтобы масштабная алгебра `n` не смешивалась с округляемой арифметикой.

## Proof-Carrying strict mode

В проект добавлен минимальный proof-carrying контур:

- `source_registry.py` строит SHA-256 реестр источников и данных. Текущий снимок лежит в `data/source-registry.json`.
- `proof_engine.py` валидирует конечный boolean-trace и возвращает один из статусов: `SOUND`, `UNKNOWN`, `REJECTED_CERTIFICATE`.
- Trusted path отвергает `float` в сертификате и запрещает proof artifacts с `Admitted`, `admit`, `sorry`, `axiom` и `unsafe`.
- `StrictProofEngine.partition_certificate()` формирует машинно-читаемый сертификат характеристической идентичности `sum_b chi_b(x) = 1` для конечного набора boolean-дельт.

Это не заменяет Rocq/Lean kernel. Это промежуточный исполняемый слой, который уже дисциплинирует данные и готовит формат сертификатов для будущей проверки внешним proof assistant.

## Формальные домены из схем

Модуль `formal_domains.py` реализует три независимых бинарных дерева:

- иерархия материи: `Field`, `FreeParticles`, `Subparticles`, `Solid`, `Liquid`, `Plasma`, `NeutralGas`;
- дискретность объекта по двум boolean-признакам: внешняя ограниченность и внутренняя прерывность;
- пары плоскостей на точных `Fraction`: `Parallel`, `Coincident`, `Perpendicular`, `Oblique`.

Каждый решатель возвращает `FormalDecision` с leaf, trace и proof obligations. Геометрия плоскостей не использует углы с плавающей точкой: перпендикулярность проверяется через точное равенство скалярного произведения нормалей нулю.

## SMT и физический GPU-контур

`smt_certificates.py` подключает `z3-solver`, если он установлен, и доказывает базовое обязательство закона исключенного третьего через проверку невыполнимости `not(P or not P)` и `P and not P`. Если `z3` не установлен, модуль возвращает явный статус `unavailable`, а не имитирует доказательство.

`galaxy_shadow.py` отделяет исследовательскую физику от trusted-core. В нем есть CPU reference, CuPy RawKernel source/builder и Numba CUDA builder для прямого `O(N^2)` взаимодействия давления/гравитационной тени. Barnes-Hut и другие группирующие приближения не используются.

`cuda/galaxy_shadow_direct.cu` задает целевой CUDA C++ backend:

- SOA layout: отдельные массивы `x/y/z/mass/vx/vy/vz/ax/ay/az`;
- tiled shared memory по `TILE_SIZE`;
- прямой проход `O(N^2)` по телам без Barnes-Hut/Particle-Mesh;
- глобальный confinement-член `-lambda * r * psi(r)`;
- Velocity Verlet drift/kick kernels для симплектического шага.

`gui_app.py` и `vispy_viewer.py` являются optional UI-adapters: DearPyGui управляет коэффициентами, VisPy показывает 3D точки и 2D кривую скоростей при наличии соответствующих пакетов.

## UI

Рабочий интерфейс должен показывать:

- активное дерево дельт и выбранную ветвь;
- виртуальный объем или текущий граф сборки;
- текущую сущность, дельту, инварианты и основание;
- журнал вычисления;
- канонический хэш текущего результата.

Текущий прототип реализует первые четыре пункта в упрощенном виде и добавляет хэш состояния.
Также он реализует текстовый запрос к ограниченному словарю понятий с дисциплиной `sound-or-unknown`.
